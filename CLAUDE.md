# terraform-provider-cosmoner

The Terraform provider for Cosmoner, in Go on `terraform-plugin-framework`. It
manages Cosmoner resources through the public API, with the same API keys and
`COSMONER_*` environment variables as the SDKs and CLI in
`datablock-dev/cosmoner-sdk`.

## Layout

```
main.go                     providerserver entry point, registry address
internal/client/            HTTP client: one file per API resource
internal/provider/          provider, resources, data sources, and their tests
examples/                   HCL used by the generated docs
docs/                       generated by tfplugindocs — never edit by hand
```

## Scope

Only wrap endpoints that carry an API-key scope; `API_KEY_RESOURCES` in the
platform repo (`packages/schemas/src/api-key-scopes.ts`) is the list. An
endpoint with no scope is dashboard-only.

Billable resources (apps, servers, databases, Redis, storage) are deliberately
not in yet. They provision asynchronously and bill from creation, so each needs
a decision on what `apply` waits for and what a failed provision leaves behind
before it is added.

## Conventions

- `internal/client` keeps the SDKs' transport rules: 429 is always retried,
  5xx and network failures only for idempotent methods, one idempotency key per
  logical write reused across retries, 204 has no body, and an empty body or
  `null` data on any other success is an error.
- Every project-scoped resource embeds `resourceBase`, which carries the client
  and fills `project_id` from the provider at plan time in `ModifyPlan`. It has
  to be resource-level: attribute plan modifiers run on an unconfigured
  instance and cannot see the provider's project.
- Imports take `<project_id>/<id>`, or a bare `<id>` with a provider default,
  through `importProjectScoped`.
- Server-owned vocabularies (webhook events, environments) are not validated
  client-side, so a new value does not need a provider release. Stable rules
  the API enforces (name patterns, lengths, https) are mirrored so they fail at
  plan time.
- When the API normalises input (trims names, collapses whitespace in SSH
  keys), keep the configured spelling in state if it means the same thing, or
  every apply reports an inconsistent result.
- Documentation lives in each attribute's `MarkdownDescription` and in
  `examples/`. Run `go generate ./...` after changing either and commit
  `docs/`; CI fails when it is stale.

## Things that will bite you

- **Secrets cannot be read back.** No route returns a secret's value after it
  is set. Drift is detected from `version`, which every write bumps. Never add
  a read of the value: there is no route for one, and the plaintext would end
  up in state.
- **Writes to secrets and variables need an owner or admin**, checked
  independently of the key's scopes. A 403 on a key that carries
  `secrets:write` is this, not a bug.
- **The tests run real Terraform against `internal/provider/fake_api_test.go`.**
  Any platform behaviour the provider depends on — status codes, which fields a
  response omits, how a missing field is treated on update — has to be mirrored
  in the fake, or the tests prove behaviour the real API does not have.
- **Secret creation is rate-limited per IP** (10 per 10 minutes) by the
  platform's `credentialCreationLimiter`, so an apply creating many secrets
  stops partway. That is the platform's limit, not something to retry around.

## Checks

```bash
golangci-lint run ./...
go test ./...            # needs terraform on PATH or TF_ACC_TERRAFORM_PATH

goreleaser check
```
